How I ship

Six steps, every send.

The same routine for a one-off launch email and a recurring send to millions. The checks are what make it safe to go fast.

01

Brief

One goal, one metric, one audience. What happens if we don't send?

✓ metric + holdout agreed

02

Signal

Agree the exact usage event or threshold with data and growth engineering.

✓ definition written down

03

Validate

Count vs expectation, spot-check records by hand, check edge cases.

✓ sample looks right

04

Build

Audience, suppressions, frequency rules, naming, tracking.

✓ governance rules applied

05

QA

Live proofs, links, personalisation fallbacks, sync freshness.

✓ proofs signed off

06

Monitor

Watch the first hours: bounces, complaints, clicks, errors. Pause if needed.

✓ result logged

When the same problem shows up twice, the check moves into the template so nobody has to remember it.

Programmes

Three programmes I'd want to own first.

Sketched from the outside, using only what's in the job post. The real versions start from Docker's data and the existing lifecycle lead's plan.

Admins · Renewal

Renewal automation

  1. 90 days out: value recap for the account, by usage.
  2. 60 days: low seat use or adoption → help, not a hard sell.
  3. 30 days: renewal details; high-value accounts go to the renewals rep.
  4. After renewal: what's new since they signed.

metric renewal rate · owner split automated vs rep

PQLs · First touch

PQL first-touch

  1. Signal fires: usage threshold or team growth on a free plan.
  2. Automated first touch from a named person, about their usage.
  3. Reply or high intent → BDR, with context.
  4. No reply → useful nurture, re-checked on new signals.

metric PQL → meeting · guardrail no double-touch with BDR

Developers · AI products

Activation for new AI tools

  1. Already uses Docker Desktop, hasn't tried the new capability.
  2. One email + in-product tip: the problem it solves, one command.
  3. Tried it once → second use case, not a sales pitch.
  4. Repeat use → invite to give feedback or join the community.

metric first use → repeat use · holdout 10%

Copy

From signal to message.

My own samples, based only on the job post. Not real Docker messages; product details would be checked with the product team.

EmailAdmin · renewal 60d

signal: renews in 60d · 31 of 50 seats active

Your team's renewal is in 60 days. Here's your usage.

Hi Priya, 31 of your 50 seats were active last month. Before you renew, it's worth checking who still needs access and who hasn't been set up yet.

We've put the list in your admin console. Questions? Reply and it reaches your account manager.

Why: admins trust a renewal email that helps them get it right, even if it means fewer seats now.

EmailPQL · first touch

signal: 12 developers on a free plan · same company domain

12 people at Acme are building with Docker

Hi Tom, it looks like your team has grown around Docker. At this size, most teams start asking about central admin, access control and image policies.

If that's on your list, I can share how similar teams set it up. If not, no follow-up.

Why: uses the signal honestly, offers something useful, and promises not to chase. Sent from a real person.

In-productDeveloper · AI

signal: active Desktop user · hasn't tried Sandboxes

Letting an agent run code? Give it a sandbox.

Run your coding agent in an isolated environment, so it can build and test without touching the rest of your machine.

Try it on your current project.

Why: starts from a worry developers already have, explains the benefit in one line, and points to their own work.
